## User Constraints (from CONTEXT.md)

### Locked Decisions

#### Training Mix Strategy

- **D-01:** Tok3 should train on a balanced domain mix: use all of domain 2
  and a deterministic sampled subset of larger domain 1 so tokenizer 3 does
  not become Twitter-heavy.
- **D-02:** Deduplication should be exact-line dedup only after mixing. Do not
  lowercase or normalize for dedup, because casing and punctuation may carry
  domain-specific NER signal.

#### Candidate Sweep and Selection

- **D-03:** Tok3 should sweep vocab sizes `4000`, `8000`, and `16000` rather
  than defaulting to the current Phase 2 vocab-8000 baseline.
- **D-04:** Final tok3 selection should use a hidden-generalization score:
  balance held-out cross-domain efficiency, VM F1, OOV robustness, zero-UNK
  behavior, reconstruction/alignment safety, and checker gates. Do not choose
  solely by lowest tokens/char.

#### VM Evidence

- **D-05:** Phase 4 should run VM F1 evaluation for all tok3 vocab candidates
  before final selection. This intentionally pulls some VM work forward from
  Phase 5; the plan must include a budget stop-rule to protect the 10h Tesla
  M60 allocation.
- **D-06:** Tok3 VM F1 should cover visible NER domains for each tok3
  candidate, with deterministic result rows and logs, so Phase 5 can reuse the
  evidence instead of repeating avoidable runs.

### the agent's Discretion

- Define the exact deterministic sampling mechanism for choosing domain-1
  lines, as long as it is reproducible from project files and documented in
  `train_commands.txt` or a helper script.
- Define the concrete hidden-generalization score formula, as long as it
  implements D-04 and remains auditable from CSV evidence.
- Choose whether to create a helper file for mix generation and/or tok3
  evaluation, while preserving the unedited course scaffold files.

### Deferred Ideas (OUT OF SCOPE)

- Full final competition measurement for all three tokenizers remains Phase 5,
  although Phase 4 will produce reusable tok3 VM evidence.
- Final report composition remains Phase 6.
- Advanced tokenizer optimizations such as merge regularization or
  Twitter-specific preprocessing remain v2 unless the Phase 4 evidence shows a
  clear need.

## Mix Generation Strategy

Use a helper such as `code/make_tok3_mix.py` or `code/tok3_mix.py` that reads `data/domain_1_train.txt` and `data/domain_2_train.txt`, writes `data/tok3_mix_d1sample_d2all_seed42.txt`, and writes sidecar metadata to `tuning/results/tok3_mix_manifest.json`. [VERIFIED: local file audit]

Recommended deterministic sample: hash each exact domain-1 line together with its 0-based line number and seed `42`, sort by `(hash, line_number)`, take the first 319,696 rows, then concatenate sampled domain 1 rows plus all domain 2 rows and exact-line dedup in first-seen order. [ASSUMED] The line number in the hash avoids unstable treatment of repeated identical lines before the required post-mix exact dedup. [ASSUMED]

Manifest fields should include `seed`, `domain_1_input`, `domain_2_input`, `domain_1_lines_total=1280000`, `domain_2_lines_total=319696`, `domain_1_sample_lines=319696`, `domain_1_unique_lines=1266231`, `domain_2_unique_lines=316448`, `post_mix_lines`, `post_mix_duplicate_lines_removed`, `output_file`, and SHA-256 hashes of inputs and output. [VERIFIED: local file audit]

Do not lowercase, strip internal punctuation, normalize Unicode, or near-dedup because the locked context requires exact-line dedup only after mixing. [CITED: .planning/phases/04-tokenizer-3-hidden-domain-generalization/04-CONTEXT.md]

## Hidden-Generalization Scoring

Use a deterministic selection CSV at `tuning/results/tok3_selection.csv` with one row per vocab size. [ASSUMED] Exclude any candidate from selection if it fails reconstruction, emits `[UNK]`, has no bigram, has any trigram token, fails `align_check.py`, fails `speed_check.py`, or fails `check_submission.py`. [VERIFIED: codebase grep]

Recommended normalized score:

```text
score =
  0.35 * mean_visible_f1_norm
+ 0.25 * combined_visible_tokens_per_char_norm_lower_is_better
+ 0.15 * domain_balance_norm_lower_gap_is_better
+ 0.10 * oov_robustness_norm
+ 0.10 * reconstruction_alignment_gate
+ 0.05 * speed_norm_higher_is_better
```

`mean_visible_f1_norm` should average tok3 F1 on visible domain 1 and domain 2. [ASSUMED] `domain_balance_norm_lower_gap_is_better` should reward smaller absolute gaps between domain-1 and domain-2 tokens/char and F1, because hidden-domain generalization should not look like a single-domain tokenizer. [ASSUMED] `oov_robustness_norm` should be 1 only when all stress cases reconstruct and emit zero `[UNK]`; otherwise it should drop sharply or gate out the candidate. [ASSUMED]

Tie-breakers: choose the smaller vocab if scores differ by less than `0.01`, then choose lower combined visible tokens/char, then choose higher worst-domain F1, then choose faster encoding. [ASSUMED] This aligns with GEN-01 by valuing balanced data behavior, GEN-02 by gating zero-UNK/OOV robustness, and GEN-03 by producing auditable evidence for report claims. [CITED: .planning/REQUIREMENTS.md]

## Common Pitfalls

### Pitfall 1: Domain-1 Dominance
**What goes wrong:** Tok3 behaves like a Twitter-heavy tokenizer because raw domain 1 has about 4.0x as many training lines as domain 2. [VERIFIED: local file audit]  
**How to avoid:** Sample exactly 319,696 domain-1 lines to match domain 2 before post-mix dedup. [VERIFIED: local file audit]  
**Warning signs:** Domain-1 tokens/char or F1 is strong while domain-2 metrics degrade sharply. [ASSUMED]

### Pitfall 2: Reproducibility Drift
**What goes wrong:** A manually edited mix file or undocumented sampling method cannot be reconstructed for `train_commands.txt`. [ASSUMED]  
**How to avoid:** Commit the helper and manifest; record the helper command plus generator command. [ASSUMED]  
**Warning signs:** Mix manifest lacks input/output hashes or exact sample count. [ASSUMED]

### Pitfall 3: Hidden-Domain Overfit by Vocab Size
**What goes wrong:** Vocab 16000 may improve visible tokens/char while learning more domain-specific merges. [ASSUMED]  
**How to avoid:** Require VM F1 and OOV stress evidence and use smaller-vocab tie-breakers. [ASSUMED]  
**Warning signs:** 16000 wins efficiency but has worse worst-domain F1, wider domain gap, or lower stress reconstruction. [ASSUMED]

### Pitfall 4: VM Budget Waste
**What goes wrong:** Running six NER jobs after a slow first run can consume too much of the 10-hour budget. [CITED: .planning/PROJECT.md]  
**How to avoid:** Run one measured pilot, project total time, and stop if CUDA is unavailable or projected six-run cost exceeds 25% of remaining budget. [ASSUMED]  
**Warning signs:** `train_ner_model.py` prints `Using device: cpu` or first run wall time is much higher than Phase 3. [VERIFIED: codebase grep]

### Pitfall 5: Alignment Regression
**What goes wrong:** Any tokenizer-internal change can break the cumulative decode lengths used by `NERDataset`. [VERIFIED: codebase grep]  
**How to avoid:** Do not change `code/bpe_tokenizer.py` unless evidence forces it; keep `align_check.py` and `speed_check.py` green. [CITED: HANDOFF.md]
